# 通用申请审批系统重构规则

## 1. 项目定位

本项目重构为轻量通用申请审批系统，采用“通用申请流程 + 预置多种申请类型配置”的方案。项目重点展示 SvelteKit 全栈能力、服务端权限控制、表单配置化、状态流转、自动化测试和工程规范。

项目不是低代码表单平台，也不是企业 OA 全量实现。

## 2. 申请类型边界

预置申请类型固定为：

- 差旅申请
- 采购申请
- 报销申请
- 加班申请

每种申请类型使用代码级字段配置，字段应尽量贴近真实业务，但不支持用户在运行时新增申请类型、拖拽字段或修改校验规则。

## 3. 表单边界

所有申请都必须具备公共基础信息：

- 申请类型
- 申请标题（用户必填）
- 申请说明 / 申请原因
- 申请人信息（来自当前登录用户，不由用户手填）

各类型使用不同业务字段：

- 差旅：出发城市、目的城市、出发日期、返回日期、交通方式、预计费用等
- 采购：采购物品、采购数量、预算金额、期望到货日期、供应商建议等
- 报销：报销类型、报销金额、费用发生日期、费用说明、发票状态等
- 加班：加班日期、开始时间、结束时间、预计加班时长、调休意向等

不做采购明细表、报销明细表、发票明细表等多行表格明细。

## 4. 校验规则边界

先支持以下校验能力：

- 必填
- 文本最大长度
- 数字大于 0
- 日期不能早于今天
- 日期不能晚于今天
- 结束日期不能早于开始日期
- 结束时间不能早于开始时间
- 下拉选项必须来自配置

暂不做条件联动、异步校验、复杂公式、正则配置后台化。

## 5. 审批流程边界

统一状态流转：

```text
草稿 → 审批中 → 已通过 / 已驳回
已驳回 → 审批中
```

规则：

- 员工可以创建申请、保存草稿、编辑自己的草稿和驳回单、删除自己的草稿、提交审批、查看自己的申请
- 审批人可以查看所有非草稿申请、审批通过或驳回、查看统计
- 审批人固定为李经理
- 申请人不能审批自己的申请
- 审批人不能替申请人重新提交
- 已驳回申请由申请人编辑原申请后重新提交，原审批记录保留

暂不做多级审批、会签、加签、转交、抄送、催办、撤回和动态审批流配置。

## 6. 数据与统计边界

继续使用进程内存数据，不接数据库。预置数据需要覆盖四种申请类型、多个员工、多个部门、多个状态和多个自然月，以便页面和统计更接近真实演示效果。

统计从“差旅统计”升级为“申请统计”，推荐口径：

- 申请类型分布
- 申请状态分布
- 部门申请数量
- 月度申请趋势
- 审批通过率
- 金额趋势

金额统计只统计具备金额字段的申请类型：差旅、采购、报销。加班不参与金额统计。

## 7. SvelteKit 使用规则

本轮重构需要使用 SvelteKit form actions 重写核心表单提交能力，包括：

- 创建 / 保存草稿
- 提交审批
- 编辑草稿或驳回单
- 审批通过 / 驳回

页面数据加载应优先使用 `load` / `+page.server.ts`，减少纯 `onMount + fetch` 的页面级数据装载。API 仍可保留给组件测试、异步筛选、统计或后续扩展使用。

## 8. 分层与职责规则

继续保持依赖方向清晰：

```text
routes 页面/API → lib/server 领域服务 → lib/utils 纯函数 → lib/types 类型
```

约束：

- 页面负责展示、交互和调用 form actions，不直接改写服务端状态
- `lib/server` 负责仓储、权限、领域错误、种子数据和服务端业务规则
- `lib/utils` 保持无 I/O，便于单元测试
- `lib/components` 放可复用 UI 组件
- 申请类型字段配置集中维护，页面不能散落硬编码字段规则

## 9. 错误处理规则

领域层不得依赖中文错误文案给 API 判断状态码。应使用类型化错误或错误码，例如：

```text
FORBIDDEN
NOT_FOUND
INVALID_STATUS_TRANSITION
DRAFT_ONLY
VALIDATION_FAILED
```

中文文案只负责用户展示，不作为程序分支判断依据。

## 10. 测试与覆盖率规则

目标：coverage > 80%。

必须补强：

- 申请类型配置与校验单元测试
- repository 创建、编辑、删除、提交、审批、驳回后重新提交测试
- API / form action 权限和异常分支测试
- 发起申请页、列表页、详情页、统计页关键交互测试
- 至少一条完整业务链路测试：员工创建申请 → 提交审批 → 审批人通过 → 统计变化

测试命令需要写入 README，面试官应能本地直接运行。

## 11. 工程规范规则

补齐并维护：

- ESLint
- Prettier
- coverage 命令
- `npm run lint`
- `npm run format`
- `npm run format:check`
- `npm run test:coverage`

每批重构结束至少运行：

```sh
npm run lint
npm run format:check
npm run check
npm test
npm run build
```

涉及测试覆盖率收口时额外运行：

```sh
npm run test:coverage
```

## 12. README 必须说明的简化业务

README 必须明确说明以下被有意简化的企业级能力：

- 不支持运行时自定义表单
- 不支持数据库持久化
- 不支持多级审批、会签、加签、转交、抄送
- 不支持按部门、金额或组织架构动态匹配审批人
- 不支持附件上传、发票图片和多行明细
- 不支持消息通知、催办、撤回
- 不支持复杂 RBAC 管理后台
- 不支持真实登录、SSO、OAuth
- 不支持数据库事务、并发锁和审计日志
- 不支持低代码拖拽式表单设计器

这些简化不是遗漏，而是为了在轻量项目中突出通用流程抽象、权限边界、测试和工程质量。
